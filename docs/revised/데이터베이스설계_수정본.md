# AI_JOB_COACH 데이터베이스 설계 — 현재 저장소 기준 수정본

> 저장소에 포함된 SQL과 현재 Repository 코드가 기대하는 DB 객체를 구분하여 기록한다.

## 저장소에서 재현 가능한 테이블

### `public.products`

출처: `backend_user/sql/init_products.sql`

교육용 Product API가 사용하는 상품 테이블이다.

### `app.notices`

출처: `backend_admin/sql/15_notices.sql`

| 컬럼 | 타입 | 규칙 |
|---|---|---|
| `id` | uuid | PK, `gen_random_uuid()` |
| `title` | text | NOT NULL, 공백 불가, 최대 200자 |
| `content` | text | NOT NULL, 공백 불가, 최대 20,000자 |
| `created_at` | timestamptz | 기본 `now()` |
| `updated_at` | timestamptz | 기본 `now()`, 수정 Trigger |

인덱스: `created_at DESC`, `lower(title)`.

## 관리자 코드가 기대하지만 생성 SQL이 없는 객체

| 객체 | 코드 사용 목적 |
|---|---|
| `app.user_accounts` | 사용자 목록·상세·상태 수정·삭제, JWT 사용자 확인 |
| `app.profiles` | 사용자 취업 프로필 상세 |
| `app.ai_logs` | AI 운영 로그 목록·상세 |
| `app.admin_log_summary` | 로그 KPI 뷰 |
| `app.feedback` | AI 응답 피드백 |

현재 Repository 코드가 기대하는 주요 컬럼은 다음과 같다.

### `app.user_accounts`

```text
id, login_id, role, user_exp, last_login_at, is_active,
failed_login_count, locked_until, created_at, updated_at
```

인증 데이터 저장을 위해 별도로 `password_hash`가 필요할 수 있으나 현재 관리자 응답에서는 제외한다.

### `app.profiles`

```text
user_id, target_role, skills, experience_summary, target_date,
target_company, preferred_environment, assistant_style,
daily_notification_time, assessment_score, assessment_level,
assessment_summary, assessed_at, assessment_version,
assessment_result_id, onboarding_completed_at, created_at, updated_at
```

### `app.ai_logs`

```text
id, user_id, session_id, request_id, level, endpoint, model_name,
status_code, latency_ms, error_code, message, created_at
```

### `app.feedback`

```text
id, log_id, user_id, score, comment, created_at, updated_at
```

## 현재 관계

코드가 전제로 하는 관계:

```text
user_accounts 1 ── 0..1 profiles
user_accounts 1 ── N ai_logs
ai_logs       1 ── 0..1 feedback
user_accounts 1 ── N feedback
```

`notices`는 현재 다른 테이블과 직접적인 외래키 관계가 없다.

## 설계와 마이그레이션 간 차이

- `user_accounts`, `profiles`, `ai_logs`, `feedback`의 생성 SQL이 저장소에 없다.
- 외부 Supabase에 테이블이 존재해도 새 환경에서 저장소만으로 재현할 수 없다.
- 사용자 백엔드 Product·Item 샘플과 관리자 도메인 DB가 혼재한다.
- 원본 DB 문서의 온보딩·로드맵·퀘스트·공고·Refresh Token 테이블은 현재 SQL에 없다.

## 권장 보완 순서

1. 실제 Supabase 스키마를 SQL migration으로 추출한다.
2. `user_accounts`와 `profiles`를 먼저 확정한다.
3. `ai_logs`, `admin_log_summary`, `feedback`을 추가한다.
4. 사용자 백엔드 도메인이 확정되면 로드맵·퀘스트·공고 테이블을 추가한다.
5. FK, 삭제 정책, 인덱스, RLS와 Runtime 권한을 SQL에 포함한다.
6. 문서의 컬럼명과 Pydantic Schema 이름을 동일하게 유지한다.
